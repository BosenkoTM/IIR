## 1. Цель работы

Освоить построение и сравнение классических алгоритмов текстового ранжирования
TF-IDF и BM25 на англоязычном корпусе, научиться вычислять DCG/NDCG и
**интерпретировать причины различий поисковой выдачи**.

Последний пункт принципиален для профиля подготовки: недостаточно получить число —
нужно объяснить, почему конкретное английское предложение поднялось или опустилось
в выдаче, в том числе с языковой точки зрения (синонимия, морфологическая
вариативность, перефразирование).

## 2. Постановка задачи

> Для английского вопроса требуется расположить предложения связанной статьи
> Wikipedia так, чтобы предложения, содержащие правильный ответ, находились
> как можно выше в выдаче.

| Понятие ИПС | Что это в лабораторной работе |
|---|---|
| Запрос (query) | `Question` — англоязычный вопрос из логов Bing |
| Документ | `Sentence` — одно предложение-кандидат из статьи Wikipedia |
| Истинная релевантность | `Label` ∈ {0, 1} — экспертная разметка «предложение является ответом» |
| Выдача | перестановка candidate set конкретного вопроса |
| Метрика качества | DCG@k и NDCG@k |

Формально:

```
Question → {Sentence_1, …, Sentence_n} → scores → ranking → DCG@k / NDCG@k
```

Важное архитектурное требование: **индекс (IDF и средняя длина документа) строится
по всем предложениям выбранного split**, а ранжируются только кандидаты конкретного
вопроса. Если строить индекс по 9 предложениям одного вопроса, статистика IDF и
`avgdl` станет бессмысленной.

### Почему именно WikiQA

* Релевантность **не нужно конструировать искусственно**: для каждого вопроса уже
  есть candidate set с бинарной экспертной разметкой. Это методически чище, чем брать
  набор «вопрос — один правильный ответ» и самостоятельно генерировать отрицательные
  примеры.
* Все кандидаты одного вопроса взяты из **одной и той же** страницы Wikipedia,
  поэтому слова из заголовка статьи почти не различают кандидатов — работают только
  редкие содержательные термины. Это наглядная иллюстрация смысла IDF.
* Материал полностью англоязычный, что связывает лабораторную работу со вторым
  профилем подготовки.
* Корпус открытый, компактный (≈ 7 МБ) и имеет академическую публикацию.

**Ограничение, о котором нужно знать.** WikiQA — не тематический корпус педагогики
или методики преподавания. Его предметная область — общие вопросы по Wikipedia.
Связь со специальностью достигается через англоязычную информационно-поисковую
задачу и лингвистический разбор выдачи, а не через педагогическое содержание текстов.

## 4. Краткая теория

### 4.1. TF-IDF и косинусная близость

Вес терма в документе:

$$w(t, d) = \mathrm{tf}(t, d)\cdot \mathrm{idf}(t),\qquad
\mathrm{idf}(t) = \ln\frac{1+n}{1+\mathrm{df}(t)} + 1$$

(сглаженная версия, используемая в scikit-learn по умолчанию; $n$ — число документов,
$\mathrm{df}(t)$ — число документов, содержащих терм $t$).

При `norm="l2"` строки матрицы нормированы, поэтому скалярное произведение векторов
запроса и документа равно косинусной близости:

$$\cos(q, d) = \frac{\langle q, d\rangle}{\lVert q\rVert\,\lVert d\rVert}
= \langle \hat q, \hat d\rangle$$

### 4.2. BM25 Okapi

$$\mathrm{BM25}(D, Q) = \sum_{q \in Q} \mathrm{IDF}(q)\cdot
\frac{f(q, D)\,(k_1 + 1)}{f(q, D) + k_1\left(1 - b + b\dfrac{\lvert D\rvert}{\mathrm{avgdl}}\right)},
\qquad
\mathrm{IDF}(q) = \ln\frac{N - n(q) + 0.5}{n(q) + 0.5}$$

* $k_1$ — насыщение частоты терма: каждое следующее повторение слова добавляет всё
  меньше, предел вклада равен $k_1 + 1$;
* $b$ — сила нормировки по длине документа: при $b = 0$ длина не учитывается,
  при $b = 1$ учитывается полностью;
* $\mathrm{avgdl}$ — средняя длина документа по корпусу.

Отличия от TF-IDF, которые и создают разницу в выдаче:

| Свойство | TF-IDF (косинус) | BM25 |
|---|---|---|
| Вклад частоты терма | линейный | насыщающийся |
| Нормировка длины | неявная, через $L_2$-норму вектора | явная, через $b$ и `avgdl` |
| IDF | всегда положительный | может быть отрицательным для сверхчастотных слов |
| Настраиваемые параметры | практически нет | $k_1$, $b$ |

### 4.3. DCG и NDCG

$$DCG@k = \sum_{i=1}^{k}\frac{2^{rel_i} - 1}{\log_2(i + 1)},
\qquad NDCG@k = \frac{DCG@k}{IDCG@k}$$

где $rel_i$ — релевантность документа на позиции $i$ выдачи, а $IDCG@k$ — значение
$DCG@k$ при идеальном порядке. Для бинарной разметки WikiQA $2^{rel} - 1 = rel$,
но реализовывать следует общую формулу.

Соглашение работы: если релевантных документов нет, $IDCG@k = 0$, NDCG не определён —
такой вопрос **исключается из усреднения**, а не засчитывается как нуль.

### 4.4. Важное предупреждение о единой предобработке

Библиотека `rank_bm25` не выполняет предобработку самостоятельно: запрос необходимо
обрабатывать тем же способом, что и корпус. Если TF-IDF использует встроенный
токенизатор `TfidfVectorizer`, а BM25 — `text.split()`, то сравниваются не формулы
ранжирования, а два разных пайплайна, и выводы работы недействительны.
**Токенизатор в работе один и тот же для обоих методов и для запросов, и для документов.**

## 7. Ход работы

1. **Данные.** Загрузите `WikiQA-test.tsv` любым из способов раздела 3.
2. **Исследование candidate sets.** Сколько вопросов и предложений; у какой доли
   вопросов есть ответ; среднее число кандидатов и средняя длина предложения;
   вывод одного candidate set с пометкой правильных ответов.
3. **Единая токенизация.** Нижний регистр, отбрасывание пунктуации, удаление
   английских стоп-слов. Один и тот же токенизатор для запросов и документов.
4. **TF-IDF.** Индекс по всем предложениям split; ранжирование кандидатов вопроса
   по косинусной близости.
5. **BM25.** Два индекса: с параметрами по умолчанию ($k_1 = 1.5$, $b = 0.75$) и с
   параметрами вашего варианта. Второй нужен, чтобы отделить эффект варианта от
   эффекта самого перехода TF-IDF → BM25.
6. **DCG@k и NDCG@k своими руками.** Реализация формул + проверка на искусственном
   примере через `sklearn.metrics.ndcg_score`.
7. **Сводная таблица** по методам `random`, `overlap`, `TF-IDF`, `BM25 default`,
   `BM25 variant` для $k = 5$ и $k = 10$.
8. **Per-query error analysis.** Не менее **трёх** вопросов с наибольшим значением
   $\lvert NDCG_{BM25} - NDCG_{TF\text{-}IDF}\rvert$: вывести кандидатов с их
   `Label`, длиной, числом совпавших терминов, оценками и позициями обоих методов —
   и объяснить каждое расхождение.
9. **Выводы** (5–10 предложений, со ссылкой на собственные числа).

### Что должно быть в объяснении различий (шаг 8)

* **Насыщение частоты ($k_1$).** Многократное повторение термина вопроса линейно
  вознаграждается в TF-IDF и насыщается в BM25.
* **Нормировка длины ($b$).** BM25 штрафует длину явно; $L_2$-нормировка TF-IDF
  делает это иначе — через рост нормы вектора документа.
* **Редкие термы.** Имена собственные, числа, годы и узкоспециальные слова резко
  поднимают документ у обоих методов.
* **Лексический разрыв.** Правильное предложение перефразирует вопрос
  (*invented → devised*, *formed → develops*, *big → measures 40 metres*), и оба
  классических метода ставят его низко. Такие примеры прокомментируйте
  лингвистически: синонимия, морфологическая вариативность, номинализация,
  смена залога.

> Слабый ответ: «BM25 лучше, потому что учитывает длину документа» — без примеров.
> Сильный ответ: конкретный `QuestionID`, конкретные предложения, их длины, число
> совпавших терминов и вывод о том, какой компонент формулы дал сдвиг.

## 9. Базовые ориентиры (baseline)

Предусмотрены два уровня проверки.

| Уровень | Назначение |
|---|---|
| Kaggle WikiQA + публичный Kaggle starter | убедиться, что используется тот же публичный корпус и корректно читаются файлы |
| `course baseline` в `lab_02_teacher.ipynb` | воспроизводимые значения `random`, `overlap`, `TF-IDF`, `BM25 default`, `BM25 variant` |

Обратите внимание: страница WikiQA на Kaggle — это **dataset page, а не соревнование
с leaderboard**, поэтому «превзойти Kaggle baseline» здесь нечего; Kaggle нужен как
источник данных и как ориентир по структуре файлов.

Отдельно: стандартные результаты литературы по WikiQA традиционно приводятся в
метриках **MAP/MRR** (задача answer selection), а эта работа посвящена **DCG/NDCG**.
Это разные метрики, поэтому числа из статьи EMNLP 2015 нельзя механически объявлять
«baseline NDCG». В преподавательском ноутбуке MAP/MRR считаются дополнительно —
именно чтобы показать разницу постановок.

Форма итоговой таблицы, которую нужно получить:

| method | k | queries | mean_DCG@k | mean_NDCG@k |
|---|---|---|---|---|
| random | 5 / 10 | … | … | … |
| overlap | 5 / 10 | … | … | … |
| TF-IDF | 5 / 10 | … | … | … |
| BM25 default (1.5, 0.75) | 5 / 10 | … | … | … |
| BM25 variant | 5 / 10 | … | … | … |

Численные значения намеренно не зафиксированы в этом файле: они вычисляются самим
ноутбуком из загруженного `WikiQA-test.tsv`. Это защищает работу от расхождений,
если зеркало датасета изменит упаковку данных.

**Ожидаемый порядок результатов:** `random` < `overlap` ≲ `TF-IDF` < `BM25`.
Наивный ориентир `overlap` (сумма частот терминов запроса, без IDF и без нормировки
длины) на коротких предложениях работает на удивление прилично — именно поэтому он
является честной точкой отсчёта для вопроса «что вообще даёт IDF».

**Разница между вариантом и BM25 по умолчанию обычно мала.** Это нормальный
исследовательский результат: кандидаты WikiQA — предложения, а не длинные
веб-страницы, поэтому параметр $b$ не может дать здесь того эффекта, который он даёт
на веб-коллекциях. Оценивается корректность применения параметров и качество
интерпретации, а не «улучшение метрики любой ценой».

данных и вывод в свободной форме. Сам корпус WikiQA в репозиторий не добавляется.

## 12. Дополнительная самостоятельная работа (до +1 балла)

Достаточно **одного** из пунктов.

**А. PostgreSQL.** Загрузите кандидатов в таблицу, постройте `tsvector` и GIN-индекс,
отранжируйте кандидатов одного вопроса и сравните выдачу с Python-реализацией:

```sql
ALTER TABLE wikiqa ADD COLUMN tsv tsvector
    GENERATED ALWAYS AS (to_tsvector('english', sentence)) STORED;
CREATE INDEX wikiqa_tsv_idx ON wikiqa USING GIN (tsv);

SELECT sentence_id, label,
       ts_rank_cd(tsv, plainto_tsquery('english', :question)) AS rank
FROM   wikiqa
WHERE  question_id = :qid
ORDER  BY rank DESC;
```

`to_tsvector` выполняет собственную нормализацию текста, `plainto_tsquery`
превращает обычный пользовательский текст в `tsquery`. **Важно:** `ts_rank` и
`ts_rank_cd` — это **не** BM25: в них нет ни $k_1$, ни $b$, ни нормировки на
`avgdl`. Смысл задания — сравнить встроенное полнотекстовое ранжирование СУБД с
Python-подходом, а не утверждать эквивалентность формул.

**Б. Предобработка.** Измерьте NDCG@k при четырёх режимах (со стоп-словами и без,
со стеммингом и без) и сравните размах результатов с влиянием параметров $k_1$, $b$.

**В. Гибрид.** Объедините TF-IDF и BM25 через Reciprocal Rank Fusion
$\mathrm{RRF}(d) = \sum_m \frac{1}{60 + \mathrm{rank}_m(d)}$ и проверьте, даёт ли
это прирост. Отрицательный результат засчитывается, если он измерен и объяснён.

**Г. Answer triggering.** Попробуйте по максимальной оценке BM25 предсказать,
есть ли у вопроса ответ среди кандидатов (метрика — ROC-AUC по всем 633 вопросам),
и объясните, почему эту задачу нельзя смешивать с ранжированием.

   центре TF-IDF, BM25 и интерпретацию NDCG.
